# 任务看板分类、持久化与重试时间线设计方案

## 实施状态

截至 2026-04-09，以下内容已实现：

1. 第一阶段：任务看板分类筛选、失败摘要、重试/编辑后重试
2. 第二阶段：`project_id`、`agent_group` 持久化落库
3. 第二阶段：重试历史时间线 UI 与历史接口
4. 第三阶段：批量重试、批量审批、右侧独立详情抽屉
5. 第四阶段：自动选 Agent、自动选 Skill、低置信度人工确认

尚未实现：

1. 结构化错误码 `last_error_code`

## 1. 问题定义

当前任务看板已经具备以下能力：

1. 任务创建与执行
2. 按状态过滤
3. 展开查看任务描述、产出、执行时间
4. 查看日志
5. 任务级 Skill 选择与运行

但从当前页面和数据结构看，已经出现三个明显问题：

1. 任务数量上来后，列表缺少更细粒度的分类，难以快速定位“这是哪个项目”或“这是哪个 Agent 的任务”。
2. 失败任务只有状态展示，没有恢复动作，用户需要手工重新建任务或重复点击，操作成本高。
3. 失败信息虽然展示在详情区，但列表态缺少失败原因摘要和下一步建议，排障效率低。

从现有代码看：

1. 任务表当前只有 `agent_id`、`status`、`priority`、`skill_name`，没有独立 `project` 字段。
2. Agent 元数据已有 `group` 字段，可用于组内分类。
3. 全局组织结构 `server/org-structure.yaml` 已包含 `project` 信息，可作为任务的项目归属来源。

因此，这个问题不是“要不要分类”，而是“分类应该以什么为主键，以及如何不让筛选变复杂”。

---

## 2. 结论摘要

### 2.1 是否应该添加分类

应该添加，而且建议同时支持两层分类：

1. **主分类：项目 Project**
2. **次分类：Agent / Agent Group**

原因：

1. 这个仓虽然现在主要承载 Growth Ops 任务，但整体组织模型已经是跨项目结构，后续任务一定会跨 `Synapse-Network`、`Synapse-Network-Sdk`、`Synapse-Network-Provider`、`Spec2Flow` 等项目。
2. 用户在日常操作里最常见的两个问题就是：
   - 这个任务属于哪个项目？
   - 这个任务是谁在执行？
3. `status` 只是执行状态，不是业务定位维度；必须与项目/Agent 维度组合才可用。

### 2.2 是否应该给失败任务加“重试”按钮

应该加，但**不要直接复用同一条任务记录重新跑**，而应采用：

1. **重试 = 基于原任务复制出一条新任务**
2. 新任务继承原有 `description`、`agent_id`、`skill_name`、`context_files`
3. 新任务记录与原任务通过 `parent_task_id` / `retry_of_task_id` 建立链路

这样做的原因：

1. 保留失败现场，便于审计和排障。
2. 不会覆盖原始日志、错误原因、执行时间。
3. 可以形成“第几次尝试”的时间线，符合任务运维场景。

## 3. 结合当前项目实际情况的推荐设计

## 3.1 任务看板的核心定位

建议把任务看板从“任务列表”升级为“任务运营台”。

看板的目标不只是展示任务，而是让用户在 5 秒内回答下面四个问题：

1. 现在哪些任务卡住了？
2. 卡在哪个项目？
3. 是哪个 Agent 在执行？
4. 我下一步该重试、审批，还是修配置？

所以界面设计不应该继续围绕“单一列表 + 展开详情”，而应围绕“定位 + 操作”进行。

---

## 3.2 推荐信息架构

### 顶部：全局筛选条

顶部筛选条建议从当前的“仅状态筛选”升级为以下结构：

1. `状态`：全部 / 待执行 / 执行中 / 待审批 / 已完成 / 失败
2. `项目`：全部项目 / Synapse-Network-Growing / Synapse-Network / Synapse-Network-Sdk / Synapse-Network-Provider / Spec2Flow
3. `Agent组`：全部 / content / growth / optimization
4. `Agent`：全部 / dev_rel / seo_strategist / growth_lead ...
5. `Skill`：全部 / seo-audit / copywriting / social-content ...
6. `仅看异常`：失败 + 待审批 + 运行超时
7. `搜索框`：支持按任务标题、描述首行、Agent、Skill 搜索

设计原则：

1. 默认仅显示 `状态` 和 `项目` 两个最重要筛选。
2. `Agent组`、`Agent`、`Skill` 放进“高级筛选”抽屉，避免顶栏过载。
3. 默认排序应为：`running`、`failed`、`pending_approval`、`pending`、`completed`。

### 中部：按项目分组的任务列表

推荐默认视图不是简单平铺，而是：

1. **按项目分组 Section**
2. Section 内按状态优先级排序
3. 每条任务卡片再显示 Agent 与 Skill 标签

推荐结构：

```text
项目：Synapse-Network-Growing (12)
  失败 (3)
  执行中 (2)
  待执行 (4)
  已完成 (3)

项目：Synapse-Network-Sdk (5)
  执行中 (1)
  待审批 (1)
  已完成 (3)
```

为什么以项目分组为默认：

1. 项目是最高层上下文，最接近“责任归属”。
2. Agent 是项目内部视角，适合做二次缩小范围。
3. 当后续跨仓任务增多时，项目分组比纯 Agent 列表更稳定。

### 单条任务卡片：展示最关键的 6 个信息点

建议卡片头部固定展示：

1. 状态标签
2. 任务编号
3. 项目标签
4. Agent 标签
5. Skill 标签
6. 优先级标签

标题行只展示任务描述第一行，副标题展示：

1. 最后执行时间
2. 执行耗时
3. 最近错误摘要（失败时）

例如失败任务卡片头部应直接出现：

```text
[失败] #18 [Synapse-Network-Growing] [@seo_strategist] [seo-audit]
OPENAI_API_KEY not set
```

这样用户不需要展开详情就能看到核心失败原因。

## 3.3 分类字段应该怎么设计

### 阶段一：先做“推导型项目分类”

当前数据库没有 `project` 字段，但已有足够信息推导：

1. 任务绑定 `agent_id`
2. Agent 绑定 persona
3. `org-structure.yaml` 已定义 agent/service 属于哪个项目

因此第一阶段不需要立即改任务表，可以先在接口层补充一个只读字段：

1. `project_id`
2. `project_label`
3. `agent_group`

这能快速让前端实现项目/Agent 分类，而不需要先做数据库迁移。

### 阶段二：任务表新增显式归属字段

实现状态：已完成

本阶段已在 `TaskRow` 中新增并启用：

1. `project_id`
2. `agent_group`
3. `retry_of_task_id`
4. `attempt_no`
5. `last_error_message`

推荐字段定义：

```python
project_id = Column(Text, default="Synapse-Network-Growing")
agent_group = Column(Text, default="")
retry_of_task_id = Column(Integer, ForeignKey("tasks.id"))
attempt_no = Column(Integer, default=1)
last_error_message = Column(Text)
```

这样做的收益：

1. 列表查询更直接，不必每次 join 或推导。
2. 失败卡片可以直接显示摘要错误。
3. 重试链路可以被完整追踪。

当前实现说明：

1. 新任务创建时写入 `project_id` 与 `agent_group` 快照
2. 旧数据迁移时自动回填这两个字段
3. 后续即使 Agent 分组变更，历史任务仍保留创建当时的归属快照

## 4. 失败任务的重试设计

## 4.1 为什么要加重试按钮

从当前页面看，失败任务主要会来自三类原因：

1. 配置缺失，例如截图中的 `OPENAI_API_KEY not set`
2. 运行时错误，例如 LLM API 失败、网络错误、超时
3. 任务参数问题，例如未选择 Skill

如果没有重试按钮，用户需要：

1. 记住原任务参数
2. 回到创建表单
3. 手工重新填写并重新执行

这会让失败恢复路径非常重，尤其是在批量 SEO / 内容任务场景下。

因此应该加，而且应区分两种重试：

1. **快速重试**：不改参数，直接基于原任务复制并重新运行
2. **编辑后重试**：打开创建表单并预填原任务内容，允许修改 Skill、描述、上下文文件后再提交

## 4.2 推荐交互

失败任务卡片右上角建议提供：

1. `重试`
2. `编辑后重试`
3. `日志`

失败详情区建议增加“失败原因”和“建议动作”：

1. `失败原因`：展示结构化错误摘要
2. `建议动作`：根据错误类型给出下一步

例如：

1. `OPENAI_API_KEY not set` → 建议动作：去检查 `.env` 或切换到 `copilot`
2. `LLM API error 429` → 建议动作：稍后重试或切换模型
3. `No skill specified` → 建议动作：补选 Skill 后重试

## 4.3 后端实现原则

不建议把失败任务直接从 `failed` 改回 `running`，推荐新增接口：

`POST /api/tasks/{id}/retry`

行为如下：

1. 读取原任务
2. 创建一条新任务，复制原任务核心参数
3. `retry_of_task_id = 原任务 id`
4. `attempt_no = 原任务 attempt_no + 1`
5. 可选参数 `mode=run_now | edit_first`

返回结果：

1. 新任务对象
2. 原任务保持不变

这是最安全、最可审计的做法。

### 4.4 重试历史时间线

实现状态：已完成

第二阶段新增：

1. `GET /api/tasks/{id}/history`
2. 详情区“重试历史时间线”模块

时间线展示内容：

1. 第几次尝试
2. 对应任务 ID
3. 当前状态
4. 来源任务 ID
5. 创建/完成时间
6. 错误摘要

这样用户在查看失败任务时，可以直接看到整个重试链，而不需要手工翻日志。

## 6. 针对当前代码的落地建议

## 6.1 低成本改造，建议先做

第一批建议直接落地到现有代码：

1. 列表页新增 `Agent` 筛选
2. 列表页新增 `Agent Group` 筛选
3. 卡片头部增加 `Skill`、`priority`、失败摘要
4. `failed` 状态卡片增加 `重试` 按钮
5. `pending` 和 `failed` 统一支持“编辑后运行”
6. 列表默认排序把 `failed` 和 `running` 提前

这批改造几乎不依赖复杂迁移，收益最大。

## 6.2 第二批改造，建议跟随后端字段升级

实现状态：已完成（除 `last_error_code` 外）

第二批建议在数据层升级后再做：

1. 项目筛选与项目分组 Section
2. 重试链路时间线
3. 失败原因结构化展示
4. “仅看异常”智能视图
5. 批量重试 / 批量取消 / 批量审批

当前实现说明：

1. TaskBoard 已支持对当前筛选结果中的失败/拒绝任务进行批量重试，支持 `run_now` 与 `edit_first` 两种模式。
2. Approvals 页面已支持多选待审批项并批量批准/拒绝，复用单条审批的后端校验逻辑。
3. 任务详情已从内联展开升级为右侧抽屉，保留描述、失败原因、执行产出、重试历史与时间元信息。
4. 当前仍未实现 `last_error_code`，错误结构化能力暂时停留在 `last_error_message`。
5. 创建任务时，如果用户未显式指定 Agent 或 Skill，系统会基于任务描述、Agent goal 和 SKILL.md 描述自动推荐执行方案。
6. 当匹配置信度不足时，前端不会直接提交，而是展示候选 Agent / Skill 供用户确认。

## 7. 页面交互细节建议

### 新建任务表单

建议新增一个只读提示区：

1. 当前 Agent 所属项目
2. 当前 Agent 所属组
3. 当前 Agent 可用 Skills

这样用户在创建时就能知道任务会投递到哪个上下文。

当前实现已扩展为：

1. 用户可以不选 Agent，直接输入任务描述。
2. 系统会自动推荐 Agent / Skill，并在高置信度时自动用于创建任务。
3. 当匹配结果不稳定时，系统展示候选项并要求用户确认后再提交。

### 日志查看

当前“日志”是独立弹窗，建议保留，但增加两个能力：

1. 按时间倒序切换
2. 高亮 `error` / `started` / `completed` 关键事件

### 失败体验

失败卡片应支持一键恢复，不应要求用户重新阅读完整任务详情才能操作。

截图里的失败任务就是典型例子：

1. 错误不是业务失败，而是环境配置失败。
2. 这种失败最需要的是“去修配置”和“修完后快速重试”。

因此建议在失败卡片上增加：

1. `重试`
2. `复制任务`
3. `查看错误`

如有能力，后续还可增加：

1. `前往配置` 快捷入口

---

## 8. 最终建议

### 推荐结论

1. **要加分类**，而且推荐“项目为主、Agent 为辅”的双层分类。
2. **要加失败重试**，但推荐新建重试任务，不覆盖原任务。
3. **第三阶段已经完成批量重试、批量审批与右侧详情抽屉**，当前剩余的数据层增强项只剩 `last_error_code`。

### MVP 顺序

1. 增加 `Agent` 筛选
2. 增加 `Agent Group` 筛选
3. 失败卡片增加错误摘要
4. 失败卡片增加 `重试`
5. 增加项目推导字段，前端支持项目标签与项目筛选
6. 后端补 `retry_of_task_id`、`attempt_no`、`project_id`

这个顺序既符合当前系统现实，也能让看板从“能看”升级为“能运维”。
